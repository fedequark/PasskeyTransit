# Open CXP ZIP/JWE exporter control

The selected open implementation is [`nvinuesa/cxporter`](https://github.com/nvinuesa/cxporter), pinned at commit `96bab31fdadcfd295542bba86b8ec8bd2355294a`. Its `internal/cxp` package creates an encrypted ZIP export. Our small Go adapter loads a synthetic CXF passkey document and calls that package's `ExportResponse`. The adapter is copied into the pinned source checkout at replay time to satisfy Go's `internal` import rule. We do not modify the exporter package.

The project Python importer opens the returned ZIP, checks the index and document member names, decrypts both JWEs using a fresh recipient X25519 key, and compares the recovered passkey identity, signing key, user handle and HMAC extension state against the synthetic source. It rejects a wrong recipient and independently changed ciphertext in each member. The recovered CXF is passed to the pinned Proton Pass common 2.0.0 software authenticator; a public verifier recomputes eight ES256 signatures and eight PRF digest bindings over two repetitions and two salts. The local report is [`experiments/cxporter_cxp_open/report.json`](../experiments/cxporter_cxp_open/report.json). The clean Ubuntu run is [GitHub Actions 40350620050](https://github.com/fedequark/PasskeyTransit/actions/runs/40350620050); its original artifact ZIP has SHA-256 `e880f5a48b530caff22e7149e6b436d2a1c0451de5ca0d86a0e7c1898454cd09`.

The scoped control passed, but the exporter response **omits the required `archive` member** shown in the [FIDO CXP Working Draft response schema](https://fidoalliance.org/specs/cx/cxp-v1.0-wd-20241003.html). Its JWE uses `HPKE-Base-X25519-SHA256-AES256GCM`, distinct from the `HPKE-3-KE` JOSE profile in our separate `jwx/v4` control. The Python importer handles this specific format; compatibility with other CXP implementations is not established. `cxporter` is a CLI converter, not an installed passkey provider or a persistent destination vault. The CXF source document and Python importer are project-authored. Neither two-provider CXP interoperability nor an Android provider migration is evidenced here.

Run the public evidence check with `python tools/verify_cxporter_cxp_public_report.py --report experiments/cxporter_cxp_open/report.json`. The verifier checks retained public signatures and synthetic PRF relations; archive and decryption claims require replaying `.github/workflows/cxporter-cxp-open.yml`. The local and CI reports contain public transcripts and digests, not private keys, HMAC seeds, raw PRF values or ciphertext. A separate public vector below intentionally carries **only synthetic** plaintext and ciphertext for interoperability debugging. Two repetitions characterize this selected code path; they are not a reliability estimate.

## Second open importer cross-check

We selected the experimental [`ShaminAkarsha/cxp_poc2`](https://github.com/ShaminAkarsha/cxp_poc2) importer at commit `fee19d9ac392ffe0153bea8b917aa0a66f12b272`. With the same synthetic passkey, its own exporter and importer passed a positive control preserving ID, key, user handle and HMAC state. We then supplied that importer's recipient public key to `cxporter`. In two repetitions, `cxp_poc2`'s full response parser rejected the missing `archive` field. After bypassing the response parser solely to test the encrypted payload, its unchanged `openPayload` function rejected the first JWE with `"alg" (Algorithm) Header Parameter value not allowed`: its JOSE `dir` profile does not accept cxporter's `HPKE-Base-X25519-SHA256-AES256GCM`. The retained local result is [`cross_import_rejection.json`](../experiments/cxporter_cxp_open/cross_import_rejection.json). The public verifier checks result consistency; the rejection itself requires executing both pinned sources.

This is a measured failure between two open research implementations at a specific encryption-profile boundary. The importer does not reach the CXF document or a relying party in this cross-check. Each implementation fills unspecified details in the CXP working draft differently; the result alone does not prove a normative violation by either one. Neither project in this cross-check is an installed provider app.

There is also an **index-shape difference** behind the two observed rejection stages. The project importer decrypted `cxporter`'s index and recorded that it lacks the `{header, documents}` object required by the selected `cxp_poc2` `openPayload` implementation. `cxporter`'s pinned `archive.go` writes an `IndexDocument` with `accounts` and item metadata; `cxp_poc2`'s pinned `payload.ts` explicitly checks for `header` and `documents`. We isolated this branch with a transformed control: `cxp_poc2` first self-imported its own archive, then the adapter re-encrypted **only the decrypted synthetic cxporter index** inside that implementation's envelope. Its unchanged importer rejected the substituted index with `CxpPayloadError: index.jwe is not {header, documents}`. This is an executed layout diagnostic for an adapter-built ZIP, **not** a third rejection of the original `cxporter` ZIP. No claim is made that either index layout is required by the draft.

The index-shape check passed in [run 40355464186](https://github.com/fedequark/PasskeyTransit/actions/runs/40355464186). Its original report ZIP has SHA-256 `09255d0f0f29ce913de06c05f98981efc574d66f2c3d094662a4ad23edd43b65` and replaces the earlier cxporter CI ZIP in the staged artifact.

The same cross-check passed in [clean CI run 40353576594](https://github.com/fedequark/PasskeyTransit/actions/runs/40353576594). The original cross-report artifact ZIP has SHA-256 `cd1d9abc381e2e2ea0d1b4387da1d64c2d24eb11e4e09696438d95b9b2ada9c3` and its retained report was verified against the ZIP bytes.

The additional full-response parser control passed in [run 40354422120](https://github.com/fedequark/PasskeyTransit/actions/runs/40354422120). Its original ZIP, SHA-256 `1536898b57077d6a5902750d36baf4768512c29cecdd606b1fc937a0c227cab7`, is the version staged in the anonymous artifact.

## Retained public ciphertext vector

`experiments/cxporter_cxp_open/vectors/cxporter-poc2-v1.json` retains one actual response from the pinned `cxporter` exporter, the matching synthetic CXF source, and a test-only recipient key derivation label. The recipient IKM and passkey signing key are deliberately recoverable: **the vector must never be used with real credentials**. The ZIP contains `index.jwe` and one document JWE (plus directory entries). Its archive SHA-256 is `60927b038c4d324f0650541475f7b642b6af5bbce3da22501bddfe1bc80a8dd0`.

`python tools/verify_cxp_public_vector.py` checks the retained bytes, synthetic domain, ZIP layout, protected JWE algorithm, and digests without downloading dependencies. To replay the parser and importer, fetch `cxp_poc2` at `fee19d9ac392ffe0153bea8b917aa0a66f12b272`, install its frozen pnpm dependencies, then run `python tools/run_cxp_public_vector.py --ts-source <checkout> --vector experiments/cxporter_cxp_open/vectors/cxporter-poc2-v1.json`. That script copies only the adapter into the checkout; it invokes the implementation's own parser and `openPayload`. The full response fails on missing `archive`; adding only `archive: "deflate"` passes schema parsing; direct payload import fails on its JWE algorithm. It does not reach CXF reconstruction. The workflow also regenerates a fresh vector from pinned `cxporter` and replays it, so the retained vector and the current exporter path are separate controls. Neither outcome is a CXP conformance verdict or an installed-provider transfer.

[Clean CI run 40359254321](https://github.com/fedequark/PasskeyTransit/actions/runs/40359254321) passed both vector controls. The retained-vector replay matched archive SHA-256 `60927b038c4d324f0650541475f7b642b6af5bbce3da22501bddfe1bc80a8dd0`; the fresh ciphertext had a different SHA-256 and the same staged rejection. Both CI output JSONs are retained in `experiments/cxporter_cxp_open/ci/40359254321/` and in the local anonymous staging copy. The original GitHub artifact digest is `sha256:e079dfbe0ede2104e2e8fa161f0b4c11999bf6c5f9f8b4ed1b9a30d9ba4fb018`.

For the separate index diagnostic, `python tools/extract_cxp_public_index.py` decrypts the retained vector with a **public test-only** recipient key and verifies the source archive hash. `python tools/run_cxp_index_control.py --ts-source <checkout> --output <report.json>` then runs the selected importer on a valid self-export and on the transformed index. The local report is `experiments/cxporter_cxp_open/index_control.json`; `python tools/verify_cxp_index_control.py` checks its source binding and outcome. Replaying pinned source is still required to independently observe the import rejection.

[Clean CI run 40361395703](https://github.com/fedequark/PasskeyTransit/actions/runs/40361395703) repeated that diagnostic with a fresh PoC envelope. The positive self-import preserved one item, and the transformed index was rejected with `CxpPayloadError: index.jwe is not {header, documents}`. Its JSON report is retained in `experiments/cxporter_cxp_open/ci/40361395703/`. The original CI artifact digest is `sha256:e61ab4e12dc8e5f5073aadbb64382239aada81b285273888e44938a179ae6ce7`. The local and CI transformed ZIP hashes differ because they are freshly encrypted; neither ZIP is a `cxporter` export.

## Same-codebase RP positive control

The pinned `cxp_poc2` project also contains a local WebAuthn RP and two software providers. `python tools/run_cxp_poc2_rp_control.py --ts-source <checkout> --output <report.json>` checks four combinations: direct and indirect CXP response modes under its `spec-minimal` and `hardened` policies. Each registers a synthetic passkey with Provider A, signs in, migrates one item to Provider B, signs in with B, and signs in again with A. The probe asserts that the RP verifies each ceremony and sees one matching credential ID. The retained local report is `experiments/cxporter_cxp_open/poc2_rp_control.json`; `python tools/verify_cxp_poc2_rp_control.py` checks its source and result binding. This establishes that the PoC's own importer can populate its vault for a subsequent RP assertion. It **does not** establish transfer from `cxporter`, between independent providers, or between installed mobile apps.
