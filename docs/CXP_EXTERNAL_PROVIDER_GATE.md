# External provider transfer gates

Checked 2026-10-26. There are two distinct targets. A **CXP wire** result requires independently maintained exporter and importer code to process the same agreed CXP exchange, decrypt it, import a synthetic passkey, and later assert at an RP. An **Android platform CXF** result requires two credential-provider apps to exchange CXF through Android's provider-events API, followed by a destination assertion. A private profile accepted only by PasskeyTransit does not meet the first target; an Android transfer alone does not meet it either.

The [Android credential-transfer guide](https://developer.android.com/identity/sign-in/credential-transfer) explicitly has the exporter write `ImportCredentialsResponse(cxfJsonPayload)` to a content URI and the importer read `response.response.responseJson` as FIDO CXF JSON. It does not specify this project's CXP ZIP/JWE path. The inspected Bitwarden classes therefore give a plausible **Android CXF app-level** target, but cannot validate the private ZIP/JWE profile. The public CXP draft lacks a complete HPKE-to-JWE mapping. A separate [JOSE HPKE Internet-Draft](https://datatracker.ietf.org/doc/html/draft-ietf-jose-hpke-encrypt-22) supplies a generic JWE mapping, but does not define CXP transport or provider behavior. Proton's direct-HPKE path is a distinct implementation profile and is reported separately.

## Next executable gates

1. **CXP wire:** extend the passing Proton-exporter/Python-importer direct-HPKE test in the reverse direction, including tampering and request binding. Then find an independent implementation of the draft's ZIP/JWE profile. The current direct-HPKE result is a narrower cross-implementation exchange, not draft-conformant CXP ZIP/JWE or provider import.
2. **CXP provider:** obtain two independently maintained providers with a compatible wire profile and synthetic vaults. Capture export, destination import, and a later RP assertion against the original public key; test PRF separately. Do not substitute an internal library self-loop for this gate.
3. **Android CXF:** run two provider apps through `ProviderEventsManager` on an emulator or device. Record app, OS, API revisions, selected exporter, import receipt, and destination assertion without exposing private keys or vault dumps. This tests Android CXF migration, not the CXP draft ZIP/JWE wire format.
4. Publish a replayable transcript or a scoped external CI artifact for whichever gate actually passes. Mark inaccessible properties `NOT_EVALUABLE`; the human-reported mobile success remains contextual.
